# Data preparation — Rust entry point

Owner rule of 2026-11-12: **the data-preparation stack is Rust only.** The Python generators are archived
(`archive/python-2026-11-12/` in the research experiment that produced the current datasets), never deleted, and
superseded by `vaugelas-dataprep`. Equivalence — not byte identity — is the acceptance bar; every difference is
recorded in [PARITY.md](../PARITY.md).

**The boundary.** Training is not data preparation: the PyTorch training loop (`training/ebm_model.py`,
`featmodel.py`) stays Python and is not ported here. Everything that *produces or formats* data — the synthetic pairs,
the product-passage pairs, the candidate records the model trains and probes on — is Rust in this repository.

## Commands

The binary is `crates/vaugelas-dataprep` (build: `make dataprep`, or `cargo build --release -p vaugelas-dataprep`).

```
vaugelas-dataprep lexpairs --out DIR [--per-subtype 40] [--seed 20261112] [--contexts 16]
vaugelas-dataprep product-pairs --out DIR --src BOOKS.jsonl [--n 1989] [--seed 20261112]
vaugelas-dataprep pairs --items ITEMS.jsonl --out RECORDS.jsonl[.gz] --data DIR
vaugelas-dataprep cands -f TEXTS --out RECORDS.jsonl[.gz] --data DIR
vaugelas-dataprep --version
```

| replaces | produces |
|---|---|
| `lexpairs.py` | `DIR/lexpairs.jsonl` + `DIR/CARD.md` — synthetic lexical minimal pairs, 1,080 (40/sub-type) or 1,620 (60/sub-type) records |
| `product_pairs.py` | `DIR/items.jsonl` + `DIR/CARD.md` — minimal pairs inside real book sentences, the 1,989-item batch 1 |
| `ebm_data2.py pairs` | one record per input line, plus one per valid bad sentence with the gold form at the changed position |
| `ebm_data2.py` record path | evaluation records (`record_pf`: no gold) for arbitrary text, one JSON line per input line |

`--data DIR` needs the installed model data (the same layout as `vaugelas`): `model.frcm`, `lexicon.tsv`,
`resources/` and `lex/`. `VAUGELAS_DATA` is the fallback. The record path reads only the model's *header* (for its
fr-check rule filter), not its weights.

## Determinism

- Both generators are pure functions of `(seed, inputs)`. Seed 20261112 is the archived default and is written in the
  dataset card.
- The random stream is CPython's `random.Random` — MT19937 with `_randbelow`-based `shuffle`/`choice` — implemented in
  `src/pyrandom.rs` and pinned by a golden file generated by Python 3.12.3 (the interpreter that produced the archived
  data) and cross-checked against 3.14.4. Contract name: **`pyrandom-mt19937-v1`** (`vaugelas-dataprep --version`).
  Changing the stream is a new contract version, never a silent change of a dataset.
- Same seed and inputs ⇒ identical bytes, including the dataset card's sha256; the product-pairs card also records the
  measured wall time of *that* run, which is the only non-deterministic line in either output.

## What the datasets are, and the honest caveats

- **1,080 and 1,620 lexpairs.** The archived 213-line `lexpairs.py` is the reference; Rust reproduces both files
  byte-for-byte, `CARD.md` included (`ae10…` for 1,080, `95cc…` for 1,620). The 1,080-record
  `data/lexpairs.jsonl` that exists on disk was produced before 12:55 by the 8-context revision (git `3693633`) and is
  therefore a *different* file (`f28b…`); `--contexts 8` reproduces it exactly too. The stale file is kept, not
  overwritten.
- **1,989 product pairs.** Byte-identical (`f4a8…`) on the same 13,388 carriers, filtered, tokenised, shuffled and
  replaced exactly as Python does. The carrier corpus is public-domain book sentences and stays on the ThinkPad; it is
  not in this repository, so the test for the full batch is skipped unless `PARITY_CARRIERS` is set.
- **Candidate records.** The Rust builder is the **v14 inference path** (GEN3/GEN4, fr-check triggers, corpus atoms);
  the Python `ebm_data2.py` in the research repository is an earlier revision. On 60 items / 119 records, 113 are
  byte-identical and 6 differ only by (a) the checker's `FR_INVENTED` rule (4 records) and (b) `|capr=` suppression at
  a sentence start (2 records). The 1,962-record product batch archived on 2026-11-12 used the pre-GEN3 generator and
  a temporary `FRC_LEXPAIRS_CONF` file that no longer exists; those records are **regenerated, not copied**, and the
  parity page says so instead of claiming identity.
- **Lexical confusions are back.** That `FRC_LEXPAIRS_CONF` hook is ported as `--lexconf FILE` (same format and
  rank). On the 60-item sample the gold form is visible at the error on 45/59 bad records with the conf, 1/59 without
  it (the pre-GEN3 Python build reaches 50/59; the five-record gap is named in PARITY.md). A 143-pair equivalent
  derived from batch 1 is committed for the test, since the original temporary file is gone.

## The optional lexical-confusion resource (inference)

The candidate generator can read an extra confusion table at inference. It is **optional and off by default**:
`data-3` does not contain the file, so the shipped checker is byte-for-byte what it was.

| | |
|---|---|
| file | `<data>/resources/interp/lexpairs_conf.json` |
| format | one JSON array, `[[wrong, right, n], ...]` (the `FRC_LEXPAIRS_CONF` format); `n` is informational |
| load | `model::resources::Resources::load` (`load_lexconf`), alongside the required tables; absence is not an error |
| effect | adds candidate forms only (rank 8, exempt from the "plausible" filters, as in `ebm_cands2._lexconf`); it never changes the written form or its readings |
| disable | `VAUGELAS_NO_LEXCONF=1` (or remove the file) |
| elsewhere | `VAUGELAS_LEXCONF=/path/to/conf.json` points at another file |
| build | `vaugelas-dataprep lexconf --lexpairs data2/lexpairs.jsonl --out conf.json [--reverse]` (Rust) |

`--reverse` emits both directions of every pair. The two forms of a lexical confusion can be written either way; the
one-directional historical files came from bad sentences, where the direction was known.

**Measured on 2026-11-12 (arm `n1w_lex3`, threshold 0.9934, 55 passages + 5,000 clean book sentences):** the resource
is wired and works mechanically — with it, `faveur` in *La faveur de Dieu nous sauve* scores **0.566864** instead of
**0.000121**, because `grâce` becomes a candidate — but the product result does not move: **13 flags, a 1/17, b 1/44,
c 0/6**, identical to the arm without the resource and to the shipped N1. Clean-text false alarms go from 3.2 to
3.8 per 1,000. Only 4 of the 44 lexical defects in that corpus contain a form from the 27 lexpairs pairs, and the
scores that do rise stay below the 0.9934 operating point (the rank-vs-flag gap). **Recommendation: do not add it to
the released data set as-is**; keep the loader for experiments and future arms.

## Parity

```
cargo test --release -p vaugelas-dataprep                 # goldens, no corpus needed
make parity                                               # lexpairs + pairs, writes the table
PARITY_CARRIERS=… VAUGELAS_DATA=… PYTHON=… make parity    # all rows, including live Python re-derivation
```

The measured table, speedups and the rayon scaling of the record path are in [PARITY.md](../PARITY.md). Goldens live
in `crates/vaugelas-dataprep/tests/parity/` and are produced by Python, not by Rust.
